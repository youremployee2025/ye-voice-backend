# CI/CD Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Add config-as-code CI (GitHub Actions) and CD (Render blueprint for the backend, Vercel for both frontends) to all three repos, parameterized entirely by secrets so pointing at the client's Render/Vercel accounts later needs new tokens and connections only — zero code changes.

**Architecture:** Each repo gets `.github/workflows/ci.yml` (runs on every push and PR) and a guarded `workflow_dispatch` fallback deploy workflow that no-ops with a clear message when deploy secrets are absent. The backend additionally gets `render.yaml` (Render blueprint: build, migrate, health check, full env var list declared `sync: false`); the frontends get `vercel.json`. Production deploys are driven by the platforms' own Git integrations on push to `main`; the fallback workflows are manual escape hatches. Everything is verified once against temporary accounts with scratch env values, then those services are destroyed.

**Tech Stack:** GitHub Actions, `postgres:16` service container, Vitest, Prisma, Render blueprints, Vercel CLI.

**Constraints (hard):**

- **New files only** plus `package.json` script additions. Never touch `src/`, `app/`, or `prisma/` — feature branches are in flight.
- CI contains **no real secrets**: no production database or Redis URLs, no Vocobase key, no real Clerk secret. Anything boot requires is stubbed with obviously fake values. A test that cannot run on a stub is skipped in CI with a named reason, never fed a secret.
- The credential dry-run uses scratch values only: throwaway Render free Postgres, dummy `REDIS_URL`, dummy `VOCOBASE_API_KEY`/`VOCOBASE_API_URL`, dev Clerk keys on the frontends. Never the production Neon URL, production Redis, or the real Vocobase key.
- Tokens for the dry-run are ephemeral: never written to a non-gitignored file, never echoed into logs or CI.
- Target CI wall time: under ~5 minutes per repo.

**Facts this plan is built on (verified in the repos):**

- Backend boot requires only `DATABASE_URL` and `CLERK_SECRET_KEY` (`src/lib/env.ts` — `required()` returns `''` under `NODE_ENV=test`, so the test suite needs neither). Everything else defaults or fails soft at the call site.
- `/health` exists (`src/app.ts:67`).
- Tests run serially (`fileParallelism: false`), against `TEST_DATABASE_URL` only, with a guard that refuses Neon hosts (`test/setup.ts`, `scripts/test-prepare.mjs`). `npm run test:prepare` applies migrations to the test DB. No test makes a real network call by design.
- `REDIS_URL` appears in `.env.example` but nothing under `src/` reads it today. It stays declared (reserved) but is documented as currently unused.
- The full backend env surface is the union of `src/lib/env.ts` reads — enumerated in Task B3.
- Dashboard reads `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_SUPPORT_EMAIL`, plus Clerk's `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY`. Admin reads only `API_URL` (server-side; it has no Clerk).
- Background workers (renewal sweep, dialer sweep, schedule scanner, analytics ingest) run inside the web process when `WORKERS_ENABLED=true` (the default) — this is why the production Render service must be an always-on paid plan, never a free instance that sleeps.

### Task B1: CI test runner with one automatic re-run of failed files

The suite has a known ~10% flaky full-run rate from cross-file bleed. Policy: run the whole suite once; if files failed, re-run **only those files** once; a second miss fails the job for real. Vitest's `--retry` retries individual tests in-place, which does not reset cross-file state — so this is a small runner script instead.

**Files:**
- Create: `scripts/ci-test.mjs`
- Modify: `package.json` (add `"test:ci": "node scripts/ci-test.mjs"` to scripts — script addition only)

**Step 1: Write `scripts/ci-test.mjs`**

```js
// CI test runner: one full pass, then one re-run of only the failed files.
//
// The suite is known to fail ~10% of full runs on cross-file bleed — state a
// file leaves behind failing an unrelated file. Vitest's --retry re-runs the
// test inside the same polluted worker, which is exactly what does not help;
// re-running the failed FILES gives each a fresh worker and a clean DB reset.
// A file that fails twice is treated as a real failure.
import { spawnSync } from 'node:child_process';
import { readFileSync, rmSync } from 'node:fs';

const REPORT = 'vitest-report.json';

function runVitest(files) {
  const args = ['vitest', 'run', '--reporter=default', '--reporter=json', `--outputFile=${REPORT}`, ...files];
  return spawnSync('npx', args, { stdio: ['inherit', 'inherit', 'inherit'] });
}

function failedFiles() {
  let report;
  try {
    report = JSON.parse(readFileSync(REPORT, 'utf8'));
  } catch {
    return null; // no parseable report — the run crashed, not merely failed
  }
  const files = new Set();
  for (const result of report.testResults ?? []) {
    if (result.status === 'failed') files.add(result.name);
  }
  return [...files];
}

const first = runVitest([]);
if (first.status === 0) process.exit(0);

const failed = failedFiles();
rmSync(REPORT, { force: true });

if (!failed || failed.length === 0) {
  console.error('[ci-test] first pass failed without a parseable failure report — not retrying.');
  process.exit(first.status ?? 1);
}

console.error(`\n[ci-test] first pass failed in ${failed.length} file(s); re-running only those once:`);
for (const f of failed) console.error(`  - ${f}`);

const second = runVitest(failed);
rmSync(REPORT, { force: true });
if (second.status === 0) {
  console.error('[ci-test] re-run passed — first-pass failures were flake (known cross-file bleed).');
  process.exit(0);
}
console.error('[ci-test] failed on the re-run as well — treating as a real failure.');
process.exit(second.status ?? 1);
```

```yaml
  push:

jobs:
  test-and-build:

          --health-cmd "pg_isready -U postgres"
          --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      # CI carries no real secrets. The test suite runs under NODE_ENV=test,
      # where boot-required vars are excused (src/lib/env.ts); the values below
      # are stubs for anything that still wants a shape, never credentials.
      TEST_DATABASE_URL: postgresql://postgres:postgres@localhost:5432/ye_test
      DATABASE_URL: postgresql://postgres:postgres@localhost:5432/ye_test
      CLERK_SECRET_KEY: sk_test_ci_stub_never_a_real_key
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - name: Cache node_modules
        id: modules
        uses: actions/cache@v4
        with:
          path: node_modules
          key: modules-${{ runner.os }}-node22-${{ hashFiles('package-lock.json') }}
      - name: Install
        if: steps.modules.outputs.cache-hit != 'true'
        run: npm ci
      - name: Prisma generate
        run: npx prisma generate
      - name: Migrate test database
        run: npm run test:prepare
      - name: Test (one re-run of failed files)
        run: npm run test:ci
      - name: Build
        run: npm run build
```

Notes: Node 22 matches local development. `prisma generate` runs on every job because the client lives inside the cached `node_modules`. The `concurrency` block stops superseded pushes from queueing.

### Task B4: Manual fallback deploy workflow

**Files:** Create `.github/workflows/deploy-fallback.yml`

```yaml
name: Deploy (manual fallback)

# Manual escape hatch. Normal production deploys happen through Render's Git
# integration on push to main; this exists for the day that integration is
# down or a redeploy is needed without a new commit. It POSTs the service's
# deploy hook and no-ops, loudly, when the secret is absent.
on:
  workflow_dispatch:

jobs:
  trigger-render-deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Trigger Render deploy hook
        env:
          RENDER_DEPLOY_HOOK_URL: ${{ secrets.RENDER_DEPLOY_HOOK_URL }}
        run: |
          if [ -z "$RENDER_DEPLOY_HOOK_URL" ]; then
            echo "::notice::RENDER_DEPLOY_HOOK_URL is not configured on this repo — nothing to deploy. Set the secret to enable the manual fallback."
            exit 0
          fi
          curl --fail --silent --show-error --request POST "$RENDER_DEPLOY_HOOK_URL"
          echo "Render deploy triggered."
```

**Step 1:** Write. **Step 2:** Commit: `git commit -m "cd: add manual Render deploy fallback workflow"`.

### Task D3: `.github/workflows/deploy-fallback.yml`

`workflow_dispatch`; guarded no-op when `VERCEL_TOKEN` / `VERCEL_ORG_ID` / `VERCEL_PROJECT_ID` are absent; otherwise `npx vercel deploy --prod --token "$VERCEL_TOKEN" --yes` with `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID` exported (no `vercel link` needed).

```yaml
name: Deploy (manual fallback)

# Manual escape hatch. Normal production deploys happen through the Vercel
# Git integration on push to main; this deploys the current checkout with the
# Vercel CLI instead, and no-ops loudly when the secrets are absent.
on:
  workflow_dispatch:

jobs:
  vercel-deploy:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      VERCEL_TOKEN: ${{ secrets.VERCEL_TOKEN }}
      VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
      VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}
    steps:
      - name: Check deploy secrets
        id: check
        run: |
          if [ -z "$VERCEL_TOKEN" ] || [ -z "$VERCEL_ORG_ID" ] || [ -z "$VERCEL_PROJECT_ID" ]; then
            echo "::notice::VERCEL_TOKEN / VERCEL_ORG_ID / VERCEL_PROJECT_ID are not all configured — nothing to deploy. Set the three secrets to enable the manual fallback."
            echo "configured=false" >> "$GITHUB_OUTPUT"
          else
            echo "configured=true" >> "$GITHUB_OUTPUT"
          fi
      - uses: actions/checkout@v4
        if: steps.check.outputs.configured == 'true'
      - uses: actions/setup-node@v4
        if: steps.check.outputs.configured == 'true'
        with:
          node-version: 22
      - name: Deploy to Vercel (production)
        if: steps.check.outputs.configured == 'true'
        run: npx vercel@latest deploy --prod --yes --token "$VERCEL_TOKEN"
```
