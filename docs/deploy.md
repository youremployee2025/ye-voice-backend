# Deploying ye-voice-backend

The API deploys to **Render** from the blueprint in `render.yaml`. Everything is
config-as-code parameterized by secrets: pointing at a different Render account needs
only that account's Git connection and env values — no code changes.

## The always-on requirement

With `WORKERS_ENABLED=true` (the default), this process runs the platform's
background loops in-process: the DID renewal sweep, the outbound dialer sweep, the
schedule scanner, and the analytics ingest. A free Render instance sleeps when idle —
a sleeping dispatcher places no calls, releases no numbers, and collects nobody's
money. **Production must run on a paid, always-on plan** (the blueprint says
`starter`; scale up as needed). Free instances are for throwaway verification only.

## Environment variables

Names and meanings only — values are set in the Render dashboard (never committed).
All are declared `sync: false` in `render.yaml`. `PORT` and `NODE_ENV` come from
Render itself.

| Name | Meaning |
|------|---------|
| `DATABASE_URL` | Postgres connection string. Required at boot. |
| `CLERK_SECRET_KEY` | Clerk secret key (JWT verification). Required at boot. |
| `CLERK_PUBLISHABLE_KEY` | Clerk publishable key. |
| `CORS_ORIGIN` | The dashboard's origin. Sign-in works but every browser call fails until this names the real dashboard domain. May be a **comma-separated list** while a dashboard moves domains: every entry is allowed by CORS, and the **first** is where browsers are sent — the Google connect return and the CSV export links — so put the domain people should land on first. |
| `REDIS_URL` | Redis connection string. Required at boot. Backs the queue workers and the Google connect nonces; the nonce store consumes a link with `GETDEL`, so the server must be **Redis ≥ 6.2** — there is no fallback, and an older server fails every return leg with an unknown-command error. |
| `VOCOBASE_API_KEY` | Voice platform partner key. Server-side only; boot succeeds without it, the first upstream call fails without it. |
| `VOCOBASE_API_URL` | Voice platform API base (default `https://api.vocobase.com/api/v2`). |
| `VOCOBASE_VOICELINK_CONNECTION_ID` | Which VoiceLink connection the DID sync reads; needed only with more than one ACTIVE connection. |
| `VOCOBASE_WEBHOOK_SECRET` | Verifies inbound platform webhooks. Unset fails closed. Registered/rotated via the staff surface. |
| `VOCOBASE_WEBHOOK_SECRET_PREVIOUS` | The secret being rotated out; set only for the length of a rotation (runbook in `.env.example`). |
| `ADMIN_STAFF_TOKEN` | Shared staff token for `/api/admin/*` (what ye-voice-admin's `/login` asks for). Generate with `openssl rand -hex 32`. Unset rejects every request. |
| `RECORDING_TOKEN_SECRET` | Signs short-lived recording playback tokens. ≥32 chars; generate with `openssl rand -hex 32`. Unset, recordings don't play (fails closed). |
| `TRUST_PROXY_HOPS` | Proxy hops in front of the service — **1 on Render**. Wrong in either direction breaks the admin rate limiter (see `.env.example`). |
| `WORKERS_ENABLED` | Whether this process runs the background timers. Default true (single-process deployment). |
| `DIALER_ENABLED` | Master switch for outbound dialing. **Keep `false` until go-live is a deliberate decision** — this is the one module that spends real money and rings real phones. |
| `DIALER_TEST_ALLOWLIST` | While non-empty, the only numbers this deployment may dial. How a first live test is bounded to your own handsets. |
| `DIALER_SWEEP_MS`, `DIALER_MAX_CALLS_PER_SWEEP`, `DIALER_DEFAULT_ACCOUNT_CONCURRENCY`, `DIALER_MIN_BALANCE_CREDITS`, `DIALER_ATTEMPT_TIMEOUT_MINS` | Dialer pacing/blast-radius controls; defaults documented in `.env.example`. |
| `DID_DEFAULT_MONTHLY_PRICE_CREDITS`, `DID_RENEWAL_SWEEP_MS`, `DID_GRACE_DAYS`, `DID_MAX_RELEASES_PER_SWEEP` | DID rental billing controls; defaults in `.env.example`. |
| `SCHEDULE_SCAN_MS` | Campaign schedule scanner period. |
| `ANALYTICS_SYNC_ENABLED`, `ANALYTICS_SYNC_INTERVAL_MS`, `ANALYTICS_SYNC_MAX_PAGES`, `ANALYTICS_SYNC_OVERLAP_MINS`, `ANALYTICS_REFRESH_RATE_LIMIT_MAX` | Analytics ingest controls; sync is off by default and switched on per deployment. |
| `CALL_LIST_RATE_LIMIT_MAX`, `CALL_DETAIL_RATE_LIMIT_MAX`, `CALL_RECORDING_RATE_LIMIT_MAX` | Per-workspace call-history ceilings (requests/min). |
| `ADMIN_RATE_LIMIT_MAX`, `ADMIN_AUTH_FAILURE_MAX`, `ADMIN_RATE_LIMIT_WINDOW_MS` | `/api/admin/*` rate limits; the failure cap is the anti-token-guessing control. |
| `PUBLIC_API_URL` | This service's own public origin, and the address the voice platform's hosted OAuth redirects a browser back to at the end of the Google connect flow. **Required whenever `VOCOBASE_API_KEY` is set** — boot fails without it. Its host must also be allow-listed upstream; see *Google integrations* below. |
| `WALLET_LOW_BALANCE_INR`, `WALLET_TOPUP_POLL_MS` | Supplier-wallet controls: the balance under which the staff console says "critically low" (default 25000), and how often open payment links are re-read (default 120000, floor 30000). There is no callback for a paid link, so the poll is the only thing that makes one `CREDITED` while nobody is looking. Defaults in `.env.example`. |

## CI

`.github/workflows/ci.yml` runs on every push and pull request:

1. `npm ci` against a cached `node_modules` (keyed on `package-lock.json`).
2. `npx prisma generate`, then `npm run test:prepare` — migrations applied to a
   `postgres:16` **service container**, never a real database. The suite's own guard
   additionally refuses any Neon host.
3. `npm run test:ci` — the full Vitest suite, then **one automatic re-run of only the
   failed files** (`scripts/ci-test.mjs`). The suite has a known low rate of
   cross-file state bleed; a fresh worker and clean DB reset clears real flake, and a
   file that fails twice fails the job for real.
4. `npm run build` (tsc).

**CI holds no real secrets.** The env block in the workflow is entirely stubs (a
fake Clerk key, a fake platform key, a fake signing secret over its length floor) so
that tests exercising key-shaped code paths run against their mocks. If a future test
genuinely needs a real credential, skip it in CI with a named reason — do not add the
secret.

## Production deploys

1. Render → New → Blueprint → select this repo (install the Render GitHub app on it
   when prompted). Render reads `render.yaml`.
2. Set every env value (table above) in the service's Environment tab.
3. Deploys then happen on push to `main`. Each deploy runs
   `npx prisma migrate deploy` as the pre-deploy step, so migrations land before the
   new version starts serving; health is `/health`, and a deploy that fails its
   health check never receives traffic.

### Migrations

The pre-deploy step applies every pending migration unattended, so any migration
that needs a hand on it — manual SQL first, a backfill after, an index built
outside the deploy — is recorded here, in the same PR that adds it. A row that
says "no manual SQL needed" is the deliberate statement that a deploy of that
commit can be left alone.

| Migration | What it does / what the deploy needs |
|-----------|--------------------------------------|
| `goal_verdict` | Replaces `DoNotCall` with a per-campaign table. **The old workspace-scoped rows are NOT dropped**: if that table has any rows, it is renamed to `DoNotCall_workspace_legacy` and left in place for you to review and drop by hand — they are people who asked not to be called, and the per-campaign list starts empty, so until you deal with them nothing carries their opt-out forward. If the table is empty it is dropped and no legacy table appears. Also drops `Campaign.goalKeys` and the `CampaignContactGoal` context columns (`mergedExtraction`, `keyAttempts`, `summaryNote`), which only a goal campaign ever populated and none has run — **and it checks that**: a `DO` block ahead of the first `ALTER` raises if any campaign still carries a `goalKeys` list or `CampaignContactGoal` has any row, and the deploy stops with the whole file unapplied rather than dropping a customer's goal configuration unattended. If it fires, decide what to do with those campaigns, clear the data by hand (`UPDATE "Campaign" SET "goalKeys" = '{}'` / `DELETE FROM "CampaignContactGoal"` once dealt with), mark the refused run rolled back — `npx prisma migrate resolve --rolled-back 20260901210442_goal_verdict` — and redeploy; until the resolve, every deploy answers P3009. No manual SQL is needed for the deploy itself to succeed on a database where no goal campaign ran — but this is **not** a row you can leave alone: check afterwards whether `DoNotCall_workspace_legacy` exists, and if it does, those numbers need a decision and the table needs a manual drop once they have had one. **Not code-rollback-safe:** once this has run, the previous build cannot serve, because it selects `Campaign.goalKeys` and `DoNotCall.workspaceId`; rolling back the code needs a corrective migration ahead of it. **Behaviour change to know about:** the universal `EZO campaign opt-outs` extraction set is retired (detached from an agent on the next start of any campaign that uses it), and `stop` in the goal verdict set is the only opt-out signal left. A campaign without a goal therefore records an opt-out only when its agent carries the goal verdict set — which happens once the agent has been used by a goal campaign — and a plain campaign on an agent that never has records none. |
| `immediate_callback_minutes` | Adds `Campaign.immediateCallbackMinutes INTEGER NOT NULL DEFAULT 5` — how soon a call that dropped mid-conversation is resumed. **No manual SQL needed.** One `ADD COLUMN` with a constant default, which Postgres 11+ records in the catalogue rather than rewriting the table, on a table that holds one row per campaign. It takes a brief `ACCESS EXCLUSIVE` lock on `Campaign` and nothing else. Code-rollback-safe: the previous build never selects the column, and the column has a default so it needs no write. |
| `contact_arm_kind` | Adds the `ContactArmKind` enum (`FRESH`, `RETRY`, `FOLLOW_UP`, `RESUME`, `CALLBACK`), adds `CampaignContact.armKind` with a `'FRESH'` default, backfills it, and creates `campaign_contacts_arm_lane_idx` on `("campaignId", "status", "armKind")`. **The backfill touches `status = 'PENDING'` rows only** — three ordered `UPDATE`s, most-specific first, each excluding what the previous one claimed — because a settled contact is armed for nothing and every reader pairs the column with `status = 'PENDING'`. **Whether this needs a hand depends on one number**, so measure it before the deploy: `SELECT count(*) FROM "CampaignContact" WHERE "status" = 'PENDING';`. **Under about a million PENDING rows, no manual SQL is needed** and the deploy can be left alone — the whole file is seconds. **Above that, run it by hand first.** Two things in it do not scale: the three `UPDATE`s run inside the migration's single transaction, so the row locks are held until the file commits and the dispatcher's `FOR UPDATE SKIP LOCKED` claims skip every locked contact — the campaigns do not error, they quietly stop dialing for the length of the migration; and `CREATE INDEX` (not `CONCURRENTLY` — Prisma runs a migration in a transaction, where `CONCURRENTLY` is illegal, so this form is the only one a migration file can carry) holds `ACCESS EXCLUSIVE` on `CampaignContact` for its whole build, which blocks every claim and every contacts page outright. The manual path: run the `CREATE TYPE` and the `ALTER TABLE … ADD COLUMN` (catalogue-only, no rewrite), run the three `UPDATE`s **in batches by `campaignId`** with a commit between them, then `CREATE INDEX CONCURRENTLY "campaign_contacts_arm_lane_idx" ON "CampaignContact"("campaignId", "status", "armKind");` outside any transaction, then `npx prisma migrate resolve --applied 20260904060515_contact_arm_kind` so the deploy skips the file it would otherwise re-run. **Not code-rollback-safe:** the new build selects and writes `armKind`, and the previous build does not know the enum, so rolling back the code is fine but rolling back the schema is not. |
| `goal_enabled_switch` | Adds `Campaign.goalEnabled BOOLEAN NOT NULL DEFAULT false` — the follow-up engine's on-switch, which `Campaign.goal` had been doing by being non-blank — and backfills it with one `UPDATE` over `Campaign` from `"goal" IS NOT NULL AND btrim("goal") <> ''`, so a campaign that had a goal keeps dialing exactly as it did (`btrim` rather than `<> ''`, because a goal of spaces was the feature off and must not switch on here). **No manual SQL needed, and unlike `contact_arm_kind` there is no table size at which that stops being true.** The `ADD COLUMN` carries a constant default, which Postgres 11+ records in the catalogue rather than rewriting the table, and the backfill is **one row per campaign, not one per contact** — `Campaign` holds a row per campaign somebody created, where `contact_arm_kind`'s `UPDATE`s walk `CampaignContact` and its row above therefore tells you to count first. The whole file is seconds; the only lock is a brief `ACCESS EXCLUSIVE` on `Campaign`. **`Campaign.goal` is deliberately NOT dropped in this release.** Nothing reads it from here on — not the dial path, not the serializer, not the journey, not the validator — and the campaign PATCH accepts and ignores a `goal` field so that a dashboard deployed either side of the backend cannot 400 during the skew. The column stays one release so that the migration which stopped using the operator's own statement of what a campaign was for does not also destroy it; **a later release drops it, and that drop gets its own row here.** Code-rollback-safe, with one thing to know: the previous build reads the prose and knows nothing of the switch, so a `goalEnabled` flipped after this deploy is invisible to it — rolling the code back puts every campaign back on whatever its `goal` column still says. |
| `campaign_dial_days` | Adds `Campaign.dialDays INTEGER[] NOT NULL DEFAULT ARRAY[]::INTEGER[]` — which weekdays a campaign may dial on, `0` = Sunday. **No manual SQL needed, and no table size at which that changes.** One `ADD COLUMN` with a constant default, recorded in the catalogue rather than rewritten, on `Campaign` — one row per campaign, not per contact — and **there is no backfill at all**: empty is the unrestricted state, so every existing campaign keeps dialing on every day without a single row being touched. The only lock is a brief `ACCESS EXCLUSIVE` on `Campaign`. Code-rollback-safe: the previous build never selects the column and never writes it, and a campaign whose days were restricted after this deploy simply goes back to dialing every day until the new build returns — degraded, not wrong. **One behaviour note:** restricting days requires a `timezone`, and a campaign left with days but no zone is `incomplete`, which **pauses it** — the same fail-closed reading hours-without-a-zone already had. The dashboard form refuses to save that combination, so it is only reachable through the API. |
| `callbacks_always_on` | Sets `"callbackEnabled" = true` on every campaign that had it off, because the switch that turned it off no longer exists on any screen. **No manual SQL needed.** A single `UPDATE` over `Campaign` — one row per campaign — with no schema change, no lock beyond the rows it touches, and no index build; it is seconds on any realistic table. Count what it will touch first if you want the number for the record: `SELECT count(*) FROM "Campaign" WHERE "callbackEnabled" = false;`. **It is not reversible by re-running anything** — the previous values are not recorded — so if you need them, snapshot that id list before deploying. Code-rollback-safe in the schema sense (the column and every reader of it are unchanged), but note the previous build still renders the switch, so rolling back gives operators a control whose stored values have all been set to on. **Ordering: this backend release ships BEFORE the dashboard release that removes the switch (ye-voice-dashboard PR #32).** In that order the worst case is a dashboard still drawing a control that no longer does anything — the API accepts `callbackEnabled` and never writes it, so a stale dashboard toggling it off is a 200 and a no-op, not a 409 and not a campaign that stops booking callbacks. The other order is the one to avoid: a dashboard with the switch already gone, in front of a backend that still honours a `false`, leaves any campaign turned off before the swap with nothing anywhere able to turn it back on until this migration lands. |
| `goal_always_on` | Goal follow-ups are always on and have no budget of their own: the engine stops reading `goalEnabled`, `maxTotalDials`, `maxGoalFollowUps`, `followUpDelayHours` and `immediateCallbackMinutes`, and every contact's dial budget is `retryCount + 1` (`totalDialsFor`). The file moves the defaults of `goalEnabled` (→ `true`) and `immediateCallbackMinutes` (→ `3`) and runs one `UPDATE` setting `"goalEnabled" = true` where it was `false`. **No manual SQL needed.** Two catalogue-only default changes and one `UPDATE` over `Campaign` — one row per campaign — with no column dropped, no rewrite and no index build; seconds on any table, the only lock a brief `ACCESS EXCLUSIVE` on `Campaign`. **Not reversible by re-running anything**: the previous `goalEnabled` values are not recorded, so snapshot them first if you want the record: `SELECT id FROM "Campaign" WHERE "goalEnabled" = false;`. **Two things to know before the deploy.** (1) The over-dial-budget sweep now runs on every campaign, and it does not exempt an armed callback, so a PENDING contact of a formerly plain campaign that already holds a placed attempt at `attemptNo >= retryCount + 1` is `SKIPPED` on the first pass — a promised callback included. Count them first (production answered 0 rows on 2026-09-06): `SELECT c.id, c."retryCount", count(*) FROM "CampaignContact" cc JOIN "Campaign" c ON c.id = cc."campaignId" WHERE cc.status = 'PENDING' AND EXISTS (SELECT 1 FROM "CallAttempt" ca WHERE ca."campaignContactId" = cc.id AND ca."attemptNo" >= c."retryCount" + 1 AND ca."launchError" IS NULL) GROUP BY 1,2;` and raise `retryCount` on those campaigns before deploying if any come back. (2) Render runs this file before the new build serves, so for that window the OLD engine sees `goalEnabled = true` everywhere and applies its own goal rules at the stored knobs (`maxTotalDials` 6, `followUpDelayHours` 24 h); short and bounded. **Ordering: this backend release ships BEFORE ye-voice-dashboard PR #37**, which stops sending `goalEnabled` — in the other order the old backend defaults every new campaign to `false` and it never follows up while the new dashboard says it does. Code-rollback-safe in the schema sense (every column is still declared), **not behaviour-safe**: the previous build honours the columns, so after the migration it treats every campaign as a goal campaign paced by the inert knobs, and the old `false` values are gone. The boot sweep prepares every RUNNING campaign's agent on the first start of the new build; it is gated on `WORKERS_ENABLED`, so make sure the worker service is the one restarted. |
| `platform_topups` | Adds the `PlatformTopupStatus` enum and the `PlatformTopup` table — the local mirror of the payment links minted against YE's supplier wallet — with a unique index on `paymentOrderId` and one on `(status, expiresAt)`. **No manual SQL needed, and there is no table size at which that stops being true.** The whole file is a `CREATE TYPE`, a `CREATE TABLE` and two `CREATE INDEX`es on a table that does not exist yet: nothing is rewritten, nothing is backfilled, and the only locks are on the new table itself, so no call path and no dial claim can block behind it. Code-rollback-safe: the previous build neither reads nor writes any of it, and the table simply sits unused. Note the mirror is **not** the source of truth — the supplier is — so a rollback loses no money fact, only the console's cached copy of each link's URL and status. |
| `call_attempt_platform_error` | Adds `CallAttempt.errorCode TEXT NULL` and `CallAttempt.errorMessage TEXT NULL` — the platform's own verdict when it, not the carrier, ended a dial. **No manual SQL needed, and no table size at which that changes.** Two nullable `ADD COLUMN`s with no default, which Postgres records in the catalogue without touching a row; no backfill, no index. The only lock is a brief `ACCESS EXCLUSIVE` on `CallAttempt`, on the order of milliseconds. Code-rollback-safe: the previous build never selects or writes either column. **Ordering with the platform: none required.** The new build reads `error_code` off webhooks the platform has not deployed yet, and until it does every payload carries null, which is the pre-existing behaviour exactly; the `TELEPHONY_CREDIT_EXHAUSTED` pause and the give-back are inert until the field arrives. **One behaviour change that lands with this build regardless of the platform:** a `no_answer` / `busy` / `failed` outcome carrying `answered_by: human` is now settled as a conversation and the contact's disposition written as `completed`; the reached count and the lead buckets read the same rule off the attempt row, so campaigns whose cause-16 calls were labelled `no_answer` will see `reached` and the outcome bar's reached tier both rise. Contacts settled `FAILED` under the old rule are not regraded by this migration — count them first if the platform's cause-16 mapping is already live: `SELECT count(*) FROM "CampaignContact" cc WHERE cc.status = 'FAILED' AND EXISTS (SELECT 1 FROM "CallAttempt" ca WHERE ca."campaignContactId" = cc.id AND LOWER(ca."answeredBy") = 'human' AND ca."disposition" IN ('no_answer','busy','failed'));`. |
| `campaign_halt_reason` | Adds `Campaign.haltReason TEXT NULL` — why a campaign is not dialing, as the sentence the campaign page prints. **No manual SQL needed, and no table size at which that changes.** One nullable `ADD COLUMN` with no default on `Campaign` (one row per campaign), catalogue-only, no backfill, no index; a brief `ACCESS EXCLUSIVE` on `Campaign`. Code-rollback-safe: the previous build never selects or writes it. **No backfill, deliberately:** a campaign paused before this deploy shows no reason on its page (the dashboard falls back to "check your notifications") until it is resumed and halted again; the notification row is still the record. **Deploy order with ye-voice-dashboard:** either. The dashboard reads `haltReason` and `failure_reason` / `failureReason` as optional and falls back to today's wording when they are absent, so a dashboard ahead of this backend degrades to the current page and a backend ahead of the dashboard is ignored. |
| `call_attempt_reached_index` | Adds `call_attempts_campaign_reached_idx` on `"CallAttempt" ("campaignId", "campaignContactId")` **partial on `disposition IN ('completed','transferred')`**, so the campaign list's connect partition and the analytics report's per-ordinal split can fold a campaign's conversations without reading every attempt it ever made. **Whether this needs a hand depends on one number**, so measure it before the deploy: `SELECT count(*) FROM "CallAttempt";` — **every** attempt, not the reached ones. A partial index is *small*, but building it still scans the whole table to find the rows that match its predicate, so the build cost is driven by the table and only the resulting index is driven by the predicate. **Under about two million attempts, no manual SQL is needed** — the build is seconds to a couple of minutes. **Above that, build it by hand first.** `CREATE INDEX` here is not `CONCURRENTLY` (Prisma runs a migration in a transaction, where `CONCURRENTLY` is illegal, so this form is the only one a migration file can carry) and it holds `ACCESS EXCLUSIVE` on `CallAttempt` for the whole build — the table the dialer inserts into on **every** dial, so a long build does not slow the campaigns down, it stops them: every claim's attempt insert blocks until the index finishes. The manual path is the one `contact_arm_kind` documents: `CREATE INDEX CONCURRENTLY "call_attempts_campaign_reached_idx" ON "CallAttempt" ("campaignId", "campaignContactId") WHERE "disposition" IN ('completed','transferred');` outside any transaction, then `npx prisma migrate resolve --applied 20260907160000_call_attempt_reached_index` so the deploy skips the file it would otherwise re-run. **No backfill and no data change** — it is an index and nothing else. **Code-rollback-safe in both directions**: the previous build simply does not use it, and dropping it costs performance rather than correctness. **Ordering: this backend release ships BEFORE the dashboard release that draws the connect ring (ye-voice-dashboard `feat/campaign-connect-ring`).** In that order the worst case is a backend sending an `outcomes.connect` nothing reads yet. The other order is merely degraded and not wrong: the dashboard's outcome cell falls back to the old disposition bar when `connect` is absent, so a campaign row keeps reporting the older, honestly-captioned reading until this lands — it does not invent the split. |
| `campaign_retry_share` | Adds `Campaign.retrySharePercent INTEGER NOT NULL DEFAULT 0` — of the slots that reach contacts already called, the percent held for plain retries; the rest goes to promised callbacks and resumes. **No manual SQL needed, and no table size at which that changes.** One `ADD COLUMN` with a constant default on `Campaign` (one row per campaign), recorded in the catalogue rather than rewritten; no backfill, no index; a brief `ACCESS EXCLUSIVE` on `Campaign`. Code-rollback-safe: the previous build never selects or writes it, and the default needs no write. **The default is a genuine no-op** — at 0 the urgent lanes take everything they can reach and retries get what is left, which is the old ordering — so this deploy re-paces no running campaign; setting the column is opting in. **Ships with a behaviour change that does not depend on the column:** the in-flight lane count now reads `CallAttempt.kind` instead of the contact's lifetime counters, which is what made `retryConcurrency` inert on any campaign whose fresh list was exhausted; a campaign with a reservation and no fresh contacts will start dialing retries out of it on the first pass. **Ordering: this backend release ships BEFORE ye-voice-dashboard PR #40.** The dashboard sends `retrySharePercent` on every draft save and create, and a backend without the column answers 400; the other way round, an old dashboard saving without the field is fine. After the deploy, set the share on the two starved campaigns (recommended 60 on `concurrencyLimit = 11`) through the settings page or a PATCH — it is accepted in every status, RUNNING included. |
| `account_onboarding_and_transfer_ledger_types` | Adds three values to the `CreditTransactionType` enum — `ONBOARDING_TOPUP`, `ACCOUNT_TRANSFER_OUT`, `ACCOUNT_TRANSFER_IN` — for the two staff operations under `/api/admin/customers/onboard` and `/api/admin/account-transfers`. **No manual SQL needed, and no table size at which that changes.** Three `ALTER TYPE … ADD VALUE`s: catalogue-only, no table touched, no rewrite, no backfill, no index; milliseconds. (Postgres 12+ allows `ADD VALUE` inside a transaction as long as nothing in the same transaction uses the new value, and this file writes no rows, so Prisma's transactional migration runs it cleanly.) **Not code-rollback-safe in the strict sense, but harmlessly so:** an enum value cannot be removed by a plain migration, and the previous build's Prisma client does not know the three new values — a `CreditTransaction` row of one of those types written by the new build would fail to deserialize in the old build's ledger reads for that account. Nothing writes such a row until staff use the two new endpoints, so roll back before the first onboarding and there is nothing to think about; after it, roll the code forward rather than back. **Ordering: this backend release ships BEFORE the staff console release that calls the two endpoints** (ye-voice-admin `feat/admin-onboard-transfer`); the other way round is a 404 on the console's onboarding screen, not a data problem. |
| `campaign_max_dials_per_day` | Adds `Campaign.maxDialsPerDay INTEGER NOT NULL DEFAULT 2` — the most placed dials one contact may get in one calendar day of the campaign's timezone, enforced by the claim alone (a contact at the cap waits for the next local day and is never settled by it; a `CALLBACK` the person asked for is exempt). **No manual SQL needed, and no table size at which that changes.** One `ADD COLUMN` with a constant default, which Postgres 11+ records in the catalogue rather than rewriting the table; no backfill, no index, one row per campaign either way. The only lock is a brief `ACCESS EXCLUSIVE` on `Campaign`, on the order of milliseconds. Code-rollback-safe: the previous build never selects or writes the column. **The behaviour change is not in this file, it is in the build that ships with it**, and it needs reading before the deploy: `maxGoalFollowUps` and `followUpDelayHours` — inert since `goal_always_on` — are read again, so on the first pass after this deploy every RUNNING campaign starts giving a contact that has ANSWERED its own follow-up budget (the stored value, 2 on almost every row) on its own wait (`followUpDelayHours`, 24 h), instead of redialing it on the retry ladder. A contact nobody has reached is unchanged. List what the stored values are before deploying: `SELECT id, name, status, "retryCount", "maxGoalFollowUps", "followUpDelayHours" FROM "Campaign" WHERE status IN ('RUNNING','PAUSED','CREDIT_EXHAUSTED') OR "maxGoalFollowUps" <> 2 OR "followUpDelayHours" <> 24;`, and lower `maxGoalFollowUps` on any campaign that should not follow up at all — 0 settles an unfinished conversation at once. **Ordering: this backend release ships BEFORE the dashboard release that edits the three settings (ye-voice-dashboard `feat/follow-up-lane`)**, because `maxDialsPerDay` becomes a required field on the dashboard's campaign type; the other order leaves the dashboard reading a field the API does not send. |
| `inbound_campaigns_schema` (20260909144312) | Purely additive: `Agent.inboundEnabled` and `Campaign.type` (both `NOT NULL DEFAULT`, metadata-only on PostgreSQL 11+), the `CampaignType` enum, and two new tables `CampaignInboundClaim` and `CampaignInboundCall` with their indexes. **No manual SQL needed**; no backfill; a deploy of this commit can be left alone. Code-rollback-safe: the previous build reads none of the new columns. **What the deploy DOES need:** the two new env vars — `INBOUND_ENABLED` (leave `false` until the routing policy is registered) and `INBOUND_ROUTE_POLICY_SECRET` (32+ chars). ### Keeping the inbound persona on `BI → UNI`

`PATCH .../agents/:agentId/direction` takes an optional `keep: 'outbound' | 'inbound'` on a `BI → UNI` move (any other move with `keep` is a 400). `'outbound'`, the default, is the move as it always was: the base is written over the face. `'inbound'` first replaces the base's hooks with the face's, then writes the face's config onto the base, and only then runs the usual overwrite, so both sides end as the inbound persona. No migration, no manual SQL, no backfill.

**`keep: 'inbound'` depends on the Vocobase base replace-all route, `PUT /api/v2/agents/:agentId/lifecycle-hooks`, being deployed.** Until it is, the platform answers its catch-all 404 and every `keep: 'inbound'` move is refused 501 `KEEP_INBOUND_UNAVAILABLE` before anything is written; `keep: 'outbound'` is unaffected. Ship order does not matter for data: this backend can go first, and the dashboard's "keep inbound" choice simply 501s until the platform catches up. Before this backend ships, an older build silently ignores `keep` — its direction schema strips the unknown key and keeps the outbound persona, so a dashboard that ships first must not offer "keep inbound" until this backend is live. **Post-deploy check:** a `keep: 'inbound'` move on a test `BI` agent answers 200 with `kept: 'inbound'` (platform route live) or 501 `KEEP_INBOUND_UNAVAILABLE` (not yet); anything else is a bug.

**No silent overwrite.** `GET .../agents/:agentId/direction/preview?to=UNI` compares the two sides live — config through the editable keys, hooks by stage, source and settings — and answers what each choice would replace, with a fingerprint per choice. When the sides differ, the `BI → UNI` move must carry a `keep` (there is no default) and that choice's `fingerprint`; the backend recomputes it immediately before writing and answers 409 `OVERWRITE_CONFIRM_REQUIRED` (no fingerprint) or 409 `DIRECTION_PREVIEW_STALE` (either side changed since the preview), each carrying the fresh preview as `details`. Identical sides need neither.

**Snapshots and restore.** The side being replaced is saved to `AgentPersonaSnapshot` first on every overwrite, the automatic ones included; a failed save refuses the overwrite (502 `SNAPSHOT_FAILED` on a direction move, the start's 422 on an inbound start). `GET .../agents/:agentId/persona-snapshots` lists them newest first, and `POST .../persona-snapshots/:snapshotId/restore` writes one back — snapshotting the current side first, so a restore is itself undoable. An inbound snapshot restores only onto a `BI` agent (409 `RESTORE_NEEDS_BI` otherwise). **An OUTBOUND restore needs the same Vocobase route as `keep: 'inbound'`**: it writes the actions first and answers 501 `RESTORE_UNAVAILABLE`, changing nothing, until that route is in Vocobase production.

### The campaign-agent boot sweep

This release changes what a campaign's agent is asked to extract: the
`EZO campaign goals` set is replaced by `Campaign call note`, and the managed
prompt block is rewritten. That swap only ever ran when a campaign crossed into
RUNNING, so a campaign **already dialing when this deploys** would have kept the old
set indefinitely — and the old set answers a vocabulary nothing here reads any more,
which means an opt-out ("never call me again") is silently not recorded, no callback
is booked, and the contact is dialed until its caps are spent. Nothing logs a
complaint, because from every surface's point of view the call simply had no note.

The worker process therefore sweeps at startup: it finds every agent behind a RUNNING
campaign that needs preparing, deduplicates them, and re-runs the same idempotent
preparation the start path runs — one agent at a time with a 500 ms gap, because it is
a burst against the partner account every YE customer shares and a deploy restarts
every instance at once. It is fired rather than awaited, so it can neither delay nor
fail the boot, and it is gated on `WORKERS_ENABLED` (`src/services/campaignAgentSweep.ts`).
There is no environment variable for it.

**What to see after the deploy**, in the worker service's log, within a few minutes
of start:

```
[campaign] boot sweep: prepared N agent pass(es) across M running campaign(s), K sharing an agent already swept, 0 failed.
```

- `N` at least 1 whenever a campaign was RUNNING at deploy time; `prepared 0 … across 0`
  is correct and expected on a deployment where nothing was dialing.
- `failed` above 0 is a bug or a dead database, not a partner outage — every upstream
  failure inside a pass becomes an ADMIN notification instead, so also check
  **Notifications** for `campaign.goal_keys_unavailable` and
  `campaign.goal_prompt_unavailable` after this deploy specifically.
- Lines reading `[campaign] retiring "…" from ag_…; it is not "…"` are an agent being
  moved off a superseded **version** of a managed set — the set name carries a
  fingerprint of its keys, so an edited description is a new set rather than an edit
  the platform has no endpoint for. Expected at most once per agent per release that
  changes a description; a line per boot means something upstream is rewriting the set
  between deploys. **This release renames both managed sets** — `YE campaign call
  note` → `Campaign call note` and `EZO campaign callbacks` → `Campaign callbacks` —
  so expect one retiring line per agent for the branded name as well, once each.
- A `campaign.goal_keys_unavailable` notification on a release that **changed a managed
  set's content** is most likely the key-name clash: the platform refuses an attach
  whose key names are already claimed on the agent, so the new version only goes on
  after the old one comes off. `ensureManagedSetAttached` detaches first for that
  reason, and a retiring line with no notification beside it is the healthy shape.
  Confirm against the platform's own logs — a `POST /api/v2/agent/<id>/extraction-sets/<set>`
  answering **409** is the clash; YE's adapter reports it as `NAME_TAKEN`, which names
  the wrong 409.
- `boot sweep skipped: this process does not run background work` means the process
  has `WORKERS_ENABLED=false`. On a split deployment that is correct for the API
  service and **wrong for the worker service** — the sweep never ran, and the campaigns
  running at deploy are still on the old contract until somebody pauses and resumes
  them.

## Google integrations

Connecting Google Sheets, Calendar or Gmail to a workspace runs through the
platform's hosted OAuth: this service mints a connect link, the browser
consents on the platform's screen, and the platform redirects back to
`${PUBLIC_API_URL}/integrations/google/return/<nonce>`.

**That host must be on the partner user's `allowedRedirectHosts` upstream
before the feature works in an environment.** It is an ops step per
environment, arranged with the platform team — there is no API on the partner
key that can set it, deliberately, because it is the control that stops a
partner redirecting somebody's OAuth result to an address of their choosing.

Without it, `POST /customers/:id/connect-link` answers **400
`INVALID_REDIRECT_URI`**, this service reports **503
`INTEGRATIONS_NOT_CONFIGURED`**, and the dashboard tells the admin the
integration is not set up yet rather than blaming them for a value they never
supplied. Nothing else is affected: campaigns, dialing and every other surface
work exactly as before.

So, per environment:

1. Set `PUBLIC_API_URL` to this service's public origin, no trailing slash.
   The platform's `validateRedirectUri` accepts **only `https:` on the implicit
   port 443 with an exact allow-listed host**: `http://` of any kind, an
   explicit port (`https://staging.example.com:8443`), and a host that is not
   on the list are each refused as `INVALID_REDIRECT_URI`. That rules out
   `http://localhost:3001` and any non-443 staging host — local development
   needs an allow-listed **https tunnel host** (ngrok, Cloudflare Tunnel or
   similar) set as `PUBLIC_API_URL`, not the port the server listens on.
2. Ask the platform team to add that origin's **host** to the partner user's
   `allowedRedirectHosts`. It must be served over **https on 443**, and the
   match is the **exact host**: `api.example.com` does not cover
   `staging-api.example.com` or a tunnel subdomain, and a new tunnel host
   needs its own entry.
3. Confirm `CORS_ORIGIN` names the real dashboard domain: it is where the
   return leg sends the browser (`/settings/integrations?connected=…`), not
   only the CORS allow-list. With a list, it is the **first** entry.
4. Check it end to end from the dashboard's **Settings → Integrations** page.
   `?error=not_ours` means the platform named a connection this workspace's
   customer does not hold, and nothing was recorded; `?error=unavailable`
   means the connector is switched off on the platform or the workspace's
   customer is archived there, which needs the platform team rather than a
   retry.

**How long an admin has.** The connect link is minted with
`expires_in_seconds` of 1800 s, and the return nonce lives 2400 s
(`src/lib/oauthNonce.ts`) — the link's life plus the 600 s the platform keeps
its own OAuth state after the click, so any redirect the platform can still
send lands while the nonce is live. A `?error=expired` therefore means the
admin came back after that, or reused a link.

**A consent screen left open for more than 600 s does not come back here at
all.** Once the platform's OAuth state has expired it no longer knows the
partner's `redirect_uri`, so it sends the browser to the voice platform's own
dashboard (`/dashboard/settings/integrations?error=invalid_state`) instead of to
this service. That is platform behaviour and nothing on this side can catch
it; the admin simply starts again from **Settings → Integrations**.

## Rollback

Render → service → Deploys → pick the previous successful deploy → **Rollback** (or
"Redeploy" on that commit). This restores the previous build. Migrations are
forward-only: rolling back the code does not roll back the schema, so a bad
migration needs a corrective migration, never `migrate reset`.
